# Запуск на VPS

Подготовлен отдельный `compose.production.yaml`: PostgreSQL, миграции, API, сайт, Caddy, бот, уведомления, сбор источников и очистка служебных данных. Публичные порты — 80 и 443; API и база доступны только внутри Docker. ИИ вызывается через Cloud.ru, GPU на VPS не требуется.

Публичный сервер пока не развёрнут: нужны VPS с Linux и домен, направленный на его IP. Начальная оценка для демо — 2 vCPU, 4 ГБ RAM, 40 ГБ SSD; это не результат нагрузочного тестирования. Установите Docker Engine с Compose по официальной инструкции для выбранной ОС. В сетевых правилах оставьте SSH для администрирования и HTTP/HTTPS для сайта.

## Настройки

Перенесите исходники на сервер. Из корня проекта создайте конфигурацию, подставив свой домен:

```bash
python3 scripts/prepare-production.py --domain afisha.example.org
```

Команда создаёт `.env.production` со случайными паролем базы и ключом администратора. Повторный запуск не перезаписывает файл. Заполните в нём токен и имя Telegram-бота, настройки Cloud.ru и тарифы из `docs/CLOUD_RU.md`. Секреты не включайте в Git. `APP_DOMAIN` содержит только имя домена, без `https://` и пути. Пароль базы задаётся до первого запуска; изменение переменной после создания тома не меняет пароль существующей базы.

## Первый запуск

Перед переносом Telegram остановите локальные процессы того же бота: одновременно должен работать один polling-процесс и одна очередь отправки.

```powershell
docker compose stop bot notifications
```

На VPS выполните:

```bash
docker compose --env-file .env.production -f compose.production.yaml up -d --build --wait
docker compose --env-file .env.production -f compose.production.yaml ps
```

Миграции применяются до запуска API и рабочих процессов. Сборщик самостоятельно собирает события из настроенных открытых источников; на новой базе каталог сначала может быть пустым. История диалогов и подписки локальной базы при таком запуске не переносятся автоматически.

Caddy получает сертификат для настроенного домена при доступных DNS и портах 80/443. Локальная проверка конфигурации не подтверждает выдачу сертификата: после запуска откройте `https://ВАШ-ДОМЕН/health/ready`, сайт и чат, затем проверьте `/start` в Telegram. `/health` со значением `configured_unchecked` подтверждает наличие настроек модели; настоящий вызов проверяется отдельно:

```bash
uv run python scripts/check_cloudru.py --base https://ВАШ-ДОМЕН
```

Этот сценарий расходует токены и не подтверждает предложенные подписки.

## Копии и обновление

С машины с доступом к Docker проекта запускайте:

```bash
python3 scripts/backup.py --production --verify
```

Копия записывается в `backups/`; проверка восстанавливает её в отдельную временную базу и удаляет только эту временную базу. Архив содержит пользовательские данные: храните копию вне VPS в закрытом хранилище. Для регулярного резервирования настройте выполнение команды по расписанию и контролируйте успешный отчёт.

Перед обновлением сделайте копию, затем повторите `up -d --build --wait`. Не удаляйте том PostgreSQL. Остановка через `stop` сохраняет данные. Восстановление основной базы и перенос локальных пользователей следует выполнять в отдельное окно обслуживания с остановленными API и рабочими процессами; `--verify` не заменяет основную базу.

## Что проверено локально

- Production Compose проходит проверку конфигурации; опубликованы только порты прокси, cookie настроены для HTTPS.
- Caddy проходит `validate`.
- Резервная копия рабочей базы успешно восстановлена в отдельную базу: 84 события, 3 площадки, 1 подписка и 82 набора демонстрационных допущений на момент проверки.
- Тестовое уведомление отправлено настоящим Telegram-транспортом; пользователь подтвердил получение. Локальные отчёты не включены в репозиторий.

Публичная доступность, сертификат, восстановление после перезагрузки конкретного VPS и нагрузка проверяются после получения сервера и домена.

Официальная документация: [Docker Compose в production](https://docs.docker.com/compose/how-tos/production/), [автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).
